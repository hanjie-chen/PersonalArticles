# Handoff

> 这个地方有点怪的，因为 handoff.md 就是文档来着，岂不是前后矛盾了？

当一个 session 结束的时候，其中产生的内容，如果没有落实为文档或者代码，就会随着 session 结束而消失。

但是有些东西实在不太好落实，例如：

- 试过但失败的路径（不记下来，新 session 会兴冲冲重走一遍）
- 还没验证的假设
- 提过但还没定下来的约束
- 我正在做 XXX 做到一半

而这个时候，我们就需要 handoff.md 这个文档了，handoff.md 就是这些半成品的暂存区。所以它是一个归位工具，解决的是这些东西该放哪的问题。而不是一个压缩工具，它解决的不是「上下文装不下了」

### session 结束时，状态活在哪里

真正到了需要结束 session 的时候，常见的做法有四种：

1. `/clear`: 等效于新开 session(都是空窗口)，状态全部在 repo 里
2. `handoff.md`: 新开 session 读取 handoff.md 继续，状态大部分在 repo 中，少部分在 handoff.md 中
3. `/compact <instructions>`: 主动指定压缩重点，保留 session，状态还在 session 里，你挑过重点
4. `auto-compact`: 触发 agent 自动压缩，状态还在 session 里，模型替你挑的

从上往下，状态越来越易失、越来越不可验证。

auto-compact 的问题不只是黑盒，还有陈旧。它压缩的是模型当时以为的世界：文件中途改了三次，压缩后带过去的可能是改动之前的版本，而模型并不知道它过时了。换 session 则强制重读，读到的就是仓库的当前状态。

我原来的想法是把 auto-compact 和 handoff.md 当成两种压缩来比较：

- auto-compact 是被动压缩，是黑盒，你无法看见丢失了什么信息，保存了什么信息。
- handoff.md 则是主动压缩，由你可以决定（告诉模型以及可以自行修改），保存什么信息。

### 如何写一个好的 handoff.md 呢

既然 handoff.md 是归位工具，那判断标准就只有一条：能从 repo 恢复的事实，一律不写。

因为写进去有三重坏处：

- 冗余；
- 易过期；
- 一份看起来很完整的 handoff，会让新 session 觉得自己已经知道全貌了，反而不去 `git diff` 一下。写错了的事实，比没写更糟。

因此一个合格的 handoff.md 应该包含四个部分：

1. 现在在做什么，为了什么（意图，不是文件清单）
2. 下一步第一个动作
3. 负空间：试过不行的路径、排除掉的方案及其理由、还没验证的假设、说过但没写进文档的约束。这些在 git 里一个字都没有，session 一关就永久消失。因为 repo 只记录了你做了什么，从来不记录你没做什么。
4. 不完整声明：新 session 读到一份 handoff.md，是没有任何办法判断它不完整的——它会把这份文档当成全部真相，然后自信而单薄地干下去。反倒是 auto-compact 至少还留着最近几轮的原文。所以 handoff 开头要写一句话，把它定位成入口而不是全集：本文档不完整。动手前先 `git diff`，并阅读 docs/xxx.md。

#### 一个例子

```markdown
# Handoff

本文档不完整，动手前先 git diff 看当前改动。

## 在做什么
调 daily-brief 的关键词加分权重，目标是让 AI 类文章不要挤掉其他分类。正在改 config.py 里的 KEYWORD_BONUS。

## 下一步
跑 scripts/score_dump.py，对比调整前后 top 20 的分类分布。

## 负空间
- 试过用 LLM 做分类路由，token 成本翻倍且不稳定，已放弃，不要再提议
- 「AI 类不超过 top 10 的一半」这个约束是我口头说的，还没写进 docs/product.md
- 当前权重是拍脑袋定的，还没用真实数据验证过
```

handoff.md 中的内容应该及时更新，一旦确定下来，那么他就应该搬家，例如：

- 排除方案的理由稳定了 → `decisions.md`
- 口头约束确定了 → `AGENTS.md` 或 `docs/`

handoff.md 是临时暂存区，而不是信息的永久住所。

### 什么时候写

那么接下来，有一个实际的问题，什么时候写 handoff.md 呢？

其实触发条件只有一个：session 要结束了，而且里面的东西还没有落盘。

真正要分的是 session 怎么结束的，这有两种：

- 主动结束：某个 task 做完，状态干净，直接切换 session
- 被动结束：ctx 逼近上限，没办法了

这两种情况都要写 handoff，区别只在于写出来有多长。

- 主动结束时该 commit 的都 commit 了，handoff 很薄（甚至只有一句话：进行下一步task，这句话甚至可以记在你的脑子里，不用写下来）；
- 被动结束时一堆东西悬在半空，又长又难写——但正因为没得选，它才更必须写。

所以 ctx 用量是硬约束：如果等到 85% 再动手，可能连写一份像样 handoff 的余量都没有了。看到 80% 就该动手。

不过它有两重含义：

- 短期：现在必须写了，再拖来不及
- 长期：如果你经常靠它触发，说明你对 task 拆得太大了

task 阶段边界的作用也在这里——它不是 handoff 的触发条件，而是让 ctx 上限尽量不需要成为触发条件的手段。一个是收尾的理想路径，一个是兜底的硬线。

但拆分不可能永远成功，因为一个 task 能不能装进一个 session，取决于探索成本，而不是 task 本身的大小：同样一个「加个字段」的需求，在熟悉的代码里几千 token 就够，在陌生代码库里光是找到该改哪里就能烧掉几万。而探索成本在开工前是不可知的。

更极端的是探索类工作——debug、调研、方案对比——它根本没有干净的阶段边界。你不可能在「假设还没验证」的中途找到一个 task 做完的时刻，只能一直做到 ctx 快满为止。对这类工作，ctx 用量是唯一可用的信号。

handoff 就是拆分失效时的安全网，而拆分一定会失效。
